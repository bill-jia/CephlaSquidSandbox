  Your question: is the motor required for switching?

  No — not in software, at any layer:

  - Driver (software/control/serial_peripherals.py): set_disk_position sends
    D<n>, set_disk_motor_state sends N<0|1>. Two independent commands with no
    cross-reference in either direction.
  - Observation states: ConfocalSettings
    (software/control/models/observation_state.py:49) carries the irises,
    dichroic and slider; ObservationState.confocal_mode carries the disk
    position. Motor state is on neither — it's deliberately session-level, as
    the sync comment in the panel says.
  - Apply paths: ObservationStateController.apply_confocal_mode
    (software/control/core/observation_state_controller.py:384) and
    Microscope.set_confocal_mode (software/control/microscope.py:1088) both move
    the disk only. Nothing in acquisition, multipoint, or startup ever calls
    set_disk_motor_state.
  - Only callers of the motor are this GUI panel, the Dragonfly panel, and
    XLight.close(), which stops it on shutdown.

  So you can select Confocal with the disk parked, and the software will happily
  acquire that way. Physically that's near-useless — a stationary disk images
  through a static pinhole mask — so there's a real coupling that the software
  doesn't enforce or even warn about. Two things I could add if you want them:

  1. Auto-start the motor when the user switches to Confocal (and optionally
     stop it on Widefield), or
  2. Leave the control manual but grey/warn the Confocal segment while the disk
     is parked.

  I didn't do either — it changes hardware behavior rather than just its
  display, and it's your call which is right for the rig.

  One related bug I did fix while in there: both switches previously updated
  (and signal_toggle_confocal_widefield fired, recording the mode on the
  observation state) regardless of whether the threaded move actually succeeded.
  Now the display and the signal wait on the driver's answer. Covered by two
  new tests; 24 pass in tests/control/test_confocal_widget_sync.py.

  Behavior

  - Motor starts before the disk moves, so it's at speed by the time it's in the
    light path.
  - Already spinning → no N command. That matters: N has a 2.5 s read delay on
    the real unit, and an acquisition applying confocal states would otherwise
    pay it at every channel switch.
  - Motor refuses to start → logged, not raised. The disk move is what the
    caller asked for and still happens.
  - Units with has_spinning_disk_motor == False are untouched.
  - Leaving confocal leaves the disk spinning. Stopping it would cost a spin-up
    on the next switch and a spinning disk outside the light path harms nothing.
    XLight.close() still parks it at shutdown.

  The panel refreshes its motor switch from the driver once the move lands, so
  Disk Off flips to Disk On by itself when it started the disk on your behalf.

  Verified: 30 tests in test_confocal_widget_sync.py (5 new for the auto-start
  policy, 1 for the panel's switch following the spin-up), plus 55 in the
  xlight-driver and observation-state suites.

  One judgment call worth flagging: I assumed the firmware's N1 round-trip (2.5
  s) covers spin-up to speed, since that's the only wait available. If the disk
  actually needs longer to stabilize, the first frame or two after an auto-start
  could be taken at partial speed — worth watching on the rig, and easy to add
  a settle delay if you see it.

  What the two controls actually do

  Snap Images

  Added 2025-05-17 (e8b0c676, "add the ability to snap multi channel images of
  the current FOV"). Despite the name, it is a one-FOV acquisition run through 
  the full multipoint pipeline, not a live-view snap:

  - Takes every checked channel (or, with nothing checked, the current live
    state as a synthetic single channel) at the current stage position, one
    plane.
  - Forces dz=0, Nz=1, dt=0, Nt=1, no contrast AF, no laser AF, no piezo, no
    fluidics. Uses a throwaway region so the Positions table is untouched.
  - Honours Save format, Skip Saving, and the ID field. Output lands in <Saving 
    Path>/snapped_images<ID>_<timestamp>/ — note the missing separator: with ID
    test you get snapped_imagestest_2026-… (multipoint.py:4534).
  - Locks the panel, triggers the "Finalizing…" wait, writes coordinates.csv +
    acquisition.yaml, exactly like a real run.
  - It overwrites the controller's Nz/dz/Nt/AF flags, but Start Acquisition
    re-pushes all of them from the GUI (multipoint.py:3891-3903), so nothing
    sticks.

  Intended use cases: a multi-channel capture that comes out in the same on-disk
  layout and metadata as an acquisition — a reference image at a spot before a
  run, a check that the full channel set is exposed correctly before committing
  to a time-lapse, or a quick capture without registering a position. The
  live-view Snap gives you one channel and a loose TIFF; this gives you the
  whole channel set as a dataset.

  Skip Saving

  Added 2025-12-24 (PR #383). Runs the acquisition with no image writer at all:
  no TIFF/zarr/OME job, no postprocess job, downsampled well views not written,
  disk-space pre-flight skipped, size label reads "Saving disabled — no files
  written". Frames still go to the napari display — the display path never
  consults the flag.

  Intended use cases: a rehearsal — run the whole stage/AF/illumination sequence
  to check positions, focus and timing without producing data; loop-latency
  profiling without disk IO; and on this rig specifically, driving
  trigger/illumination for an external camera app where the main-camera frames
  are irrelevant.

  Gotchas: it still creates the experiment folder and coordinates.csv every run
  (stray near-empty folders); it hard-refuses online postprocessing at start
  (multi_point_controller.py:2228); and the Save format dropdown stays enabled
  while it's checked, so the two controls contradict each other visually.

  Why the panel reads as confusing

  Three structural problems, visible in the screenshot:

  1. The grid block has no grouping. Nx … Ny … FOV Overlap on one row, dz Nz … 
     dt Nt on the next — seven parameters from three unrelated concerns (tiling,
     Z-stack, time-lapse) interleaved with unaligned labels.
  2. The right column is one undifferentiated checklist: focus settings, Z-stack
     settings, saving settings, and scan-behaviour flags in one stack. "Snake
     scan" sits between "Save format" and "Keep illuminators on".
  3. The button column mixes a setting with two actions. "Laser AF: Off ▸" is a
     configuration button but is drawn the same size as Snap/Start, and "Snap
     Images" — a secondary action — is drawn as big as the primary one.

  Suggestions, roughly in order of payoff

  1. Regroup into four labelled boxes (QGroupBox or bold header + indent, like
  the Positions block already does):

  Tiling per position          Focus
    Nx [1]  Ny [1]               [ ] Contrast AF
    Overlap [10 %]  [x] Snake     Laser AF   [Off ▸]
                                  [ ] Use Focus Map
  Z-stack                      Saving
    Nz [1]  dz [1.5 µm]           Format [INDIVIDUAL_IMAGES ▾]
    From [Bottom ▾]  [ ] Set range  ~ 24 images · 190 MB
                                    (or: "Not saving — dry run")
  Time-lapse                   Scan behaviour
    Nt [1]  dt [0 s]              [ ] Keep illuminators on
                                  [x] Show live preview

  2. Fold "Skip Saving" into the Save format dropdown as a Don't save (dry run)
  entry. One control instead of two that fight; the size label already knows how
  to say "no files written"; postprocessing's refusal becomes a greyed-out
  option rather than a start-time error. This is the single change I'd recommend
  most.

  3. Make Laser AF a setting row, not a button. Move it into the Focus group at
  normal row height. Keep the big-button column for actions only.

  4. Rename and demote Snap Images. "Acquire Current FOV" (or "Acquire Here"),
  half the height of Start, with a tooltip saying it uses the checked channels
  and the current save format. Fix the folder name to snap_<ID>_<timestamp>.

  5. Grey out what doesn't apply. "Z-stack from" and "Set Z-range" when Nz = 1;
  "Update Ref" unless Laser AF is on (it currently pops an error dialog
  instead); the streaming row is already hidden this way, so there's precedent.

  6. Say what Start does with no positions. The "no positions" label could read
  "no positions — Start acquires the current field", since that's what
  acquisition_in_place silently does (multipoint.py:3866), then clears the list
  afterwards, which surprises people.

  7. Small label fixes. ID → Experiment ID with placeholder text; Next → Go to 
  Next; Update Z → Set Z from Stage; Update Ref → Recapture AF Ref; the
  unlabelled Simple ▾ combobox becomes a header Channels · Simple ▾ above the
  list.

  Items 1–3 are one afternoon of layout work in FlexibleMultiPointWidget.init_ui
  and touch no controller logic; WellplateMultiPointWidget shares nearly all of
  this code, so whatever we do should be done to both.
